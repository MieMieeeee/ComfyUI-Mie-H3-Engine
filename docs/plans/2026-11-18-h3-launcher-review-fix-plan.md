# H3 Engine 与启动器审查问题修复计划

日期：2026-11-18

本计划承接 [H3 工作台接入计划](2026-11-18-launcher-h3-workbench.md)，覆盖接入后审查发现的五项问题。H3 工作台默认端口为 `8200`，原 WebUI 工作台使用 `8199`。开发与回归使用临时环境、资产库和测试端口，部署验收在本机 ComfyUI 队列空闲时进行。

审查时 H3 Engine 为 `0e4b1295`，启动器为本地 `feat/h3-workbench-launcher` 的 `3d7a6ee`。开始前重新确认两个仓库的 HEAD、已有改动和部署包版本。启动器原有的构建参数和本机配置按工作区现状保留。整合包中的旧 EXE 曾只列出 `openjutsu`、`webui`，最终验收必须检查新打包 EXE，而不是只看源码。

## 实施顺序

| 阶段 | 问题 | 仓库 | 交付 |
| --- | --- | --- | --- |
| 1 | P1 停止节点可能终止错误进程 | H3 Engine、启动器 | 按端口和实例身份启停 |
| 2 | P1 进程级变量串改资产库 | H3 Engine，必要时 MieNodes | 各调用方显式传入自己的库路径 |
| 3 | P1 独立安装后默认工作流无法渲染 | H3 Engine、启动器 | 默认图使用引擎节点，新装环境可完成渲染 |
| 4 | P2 Git 镜像更新可能重置到旧提交 | 启动器 | 更新到实际拉取的提交，失败时保全本地数据 |
| 5 | P2 未安装时 GUI 下载入口不可达 | 启动器 | 缺失插件的环境仍能从标签页下载并安装 |

阶段 1 可独立合入。阶段 2 和 3 一起验收，避免只移除全局覆盖后让默认渲染图继续从错误的库取图。阶段 4、5 可与引擎改动并行准备，最后共同验收下载、安装、启动、渲染和更新。

## 1. 按端口和实例身份停止 H3 工作台 [P1]

涉及 `webui_node.py` 中的 `_probe`、`pid_file`、`_pid_on_port` 和 `MieH3StopWebUI.disable`，以及启动器 `core/companion/h3_runtime.py` 与 `manager.py` 的就绪、收养和停止逻辑。

- 在决定终止前核对 `/api/health` 的 `status=ok`、`app=comfyui-mie-web`、监听端口的 PID，以及进程命令行和插件入口。核对当前环境时同时使用部署路径和健康接口回传的资产归属，避免两个 junction 指向同一源码时混淆实例。进程身份查询失败则返回明确错误。
- 节点自行启动时按端口记录 PID 和进程创建时间，或者每次由监听端口反查并核验身份。已有单文件 `webui.pid` 仅作提示，以实际监听者为准。仅清理当前实例对应的记录。外部启动的进程也要经过身份校验，尤其避免对未确认归属的进程组执行停止。
- 启动、状态和停止采用一致的身份判据。端口开放但响应来自其他服务时显示占用。工作台正在执行自己的任务时显示状态，并保留用户确认后停止的路径。
- [ ] 回归用例以替身断言终止调用覆盖旧 `8199` PID、PID 被复用、无关健康响应、其他环境的 H3、同一环境正常实例和多次停止。真实验收同时运行临时 H3 实例和端口占用者，只结束目标实例，保留另一实例与 ComfyUI 队列。

## 2. 将资产库归属限定在调用方 [P1]

涉及引擎 `__init__.py`、`asset_root.py`、`mie_nodes.py`、`webapp/config.py`、`webapp/services/library.py`，以及 MieNodes 的资产节点。Craft `resolve_library_dir` 已支持显式 `library_dir`，优先复用现有接口。

- 删除 H3 Engine 导入时设置的进程级 `MIE_ASSET_LIBRARY`。H3 自有节点在与 Craft 交界处传入解析后的库路径，保留节点已有 `library_dir` 参数、调用方传入的剧本快照路径和旧工作流参数。H3 网页子进程继续显式读取所属环境的资产路径与密钥配置。
- 延续现有兼容规则。引擎自有库存在时，H3 使用自有库。旧整合包仍可读取同级 MieNodes 的已有资产。MieNodes 节点继续使用自己的库。无需把现有资产搬家。若发现其他调用方会被全局默认值影响，优先在其资产节点边界传入自己的库路径。共享包只有在现有接口确实不足时才修改并单独发布。
- [ ] 同一 Python 进程加载两个插件并交换导入顺序。两个库放同名、不同内容的资产，分别核对读取与写入路径。另测旧整合包回退、junction、显式快照路径和工作台选择的资产能由 ComfyUI 节点读到。

## 3. 让 H3 默认渲染图可以独立运行 [P1]

涉及 `mie_nodes.py`、引擎节点注册、`webapp/services/workflow.py` 和 `webapp/data/mie_h3_storyboard_movie.api.json`。当前默认图依赖 `LoadAssetV2|Mie`、`AssetToSlots|Mie`，预设还引用 `ShowAndSaveAnything|Mie`。

- 给 H3 提供有独立注册名的薄节点，复用既有 Craft 资产读取、契约和组装逻辑，覆盖默认图需要的角色图、角色音频和场景图。点清整个默认图的 MieNodes 节点依赖，替换资产与槽位节点；计划展示节点用引擎已有等价能力，或在保留预览可用的前提下从默认渲染图移除。
- 保持图像和音频槽位顺序、`MIE_ASSET` / `MIE_ASSET_ROSTER` 数据形状和历史工作流中的 `|Mie` 注册名兼容。新默认图绑定阶段 2 确立的库路径。已有用户自定义预设可以继续调用自己安装的节点。
- 在渲染预检报告后端缺少的具体节点。过渡阶段可提示安装 MieNodes；H3 默认图无 MieNodes 完成出片才算本阶段完成。启动器依赖说明要与最终渲染契约一致。
- [ ] 比较默认图的节点类型与只安装 H3 的 ComfyUI 测试实例注册表。用临时剧本、角色图、参考音频和场景图跑一次多镜头渲染，核对参考槽位、成片和音轨。再让装有 MieNodes 的环境跑原工作流，验证旧节点和资产保持可用。

## 4. 让官方源和代理源更新到同一个确定提交 [P2]

涉及启动器 `core/companion/installer.py` 的 `_pull_impl`、`pull_service` 和 `tests/unit/test_companion_installer.py`。临时仓库已经复现以 URL 拉取时只有 `FETCH_HEAD` 前进，`origin/HEAD` 仍是旧引用。

- 先确定目标分支，然后用实际选中的 URL 拉取该分支，并把本次拉取的提交解析成固定 SHA。从该 SHA 执行切换，或者使用显式 refspec 更新并读取确定的目的引用。官方源与代理源使用同一套目标选择逻辑。更新返回校验切换后的 `HEAD`，仅在前后 SHA 不同且与拉取目标相同后报告已更新。
- 干净且可快进的部署副本直接更新。检测到未提交修改、分叉或开发 junction 时提供明确提示，让已有改动可保全。资产和密钥先确认可恢复再切换。暂存过程中任一步失败、Git 切换失败或恢复失败，都应明确返回失败并保留可定位的恢复副本。
- [ ] 用两个本地 Git 仓库模拟官方、代理 URL 和滞后的 `origin/HEAD`。验证实际更新、无变化、拉取失败、分支分叉、工作区有改动及用户数据保护。确认更新日志含目标版本且不输出凭证。

## 5. 在未安装环境保留下载入口 [P2]

涉及启动器 `ui_qt/pages/advanced_services_page.py` 与 `ui_qt/pages/h3_page.py`。H3 标签在插件缺失时隐藏，下载按钮恰好位于该标签中。

- 让 H3 标签在支持安装的整合包环境始终可进入。未安装时显示「下载 H3 引擎」，已下载但缺依赖时显示安装依赖，依赖就绪后显示启动。仍沿用已有下载、依赖安装、状态轮询和日志逻辑。切换环境时重新判断路径和状态。
- [ ] 用 Qt 测试覆盖未安装、下载失败后可重试、安装完成后控件切换、已运行、环境切换，以及原 WebUI 与 OpenJutsu 标签行为。用干净测试包从 GUI 走一次下载、装依赖、启动和打开页面。

## 最终验收

- [ ] 两仓提交可分别审阅。引擎跑资产归属、默认图和安全启停回归，启动器跑安装更新、伴生服务和 Qt 页面测试。涉及 MieNodes 或共享包时另跑对应仓库回归。
- [ ] 打包新启动器并记录源码提交、EXE 版本和部署位置。实际用本机部署的 EXE 执行 `service list --json`、`service start/status/stop h3-engine`，并在「进阶服务」验证标签和日志。`8200/api/health` 返回 H3 服务与当前环境资产归属。确认原 WebUI 仍可使用 `8199`。
- [ ] 记录独立安装环境与旧整合包环境的真实验收结果，包括默认图多镜头出片、现有资产可读和停止工作台后 ComfyUI 队列状态。部署前保留上一版 EXE 与引擎提交，用于回退。
